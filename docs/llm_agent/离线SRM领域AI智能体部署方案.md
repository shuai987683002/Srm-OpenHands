# 离线固体火箭发动机（SRM）领域 AI 智能体：硬件选型、部署与训练方案

> 版本：v0.1（方案阶段，未实施）
> 定位：在**物理隔离（air-gapped）**环境中，用开源工具与开源权重，构建面向固体火箭发动机
> 领域的本地 AI 智能体，同时具备「领域知识问答 / 设计研发辅助 / 工程实践支持」三类能力，
> 并保留离线推理、编程、建模、知识图、绘图、文档编写等通用能力。
> 编制视角：SRM 总体—装药—内弹道工程 + 本地大模型工程化。
> 本文性质：**可执行方案**。所有硬件/吞吐/显存数字均给出计算公式或可复算脚本
> （`scripts/llm_sizing.py`），并标注"估算"；不含未经验证的实测宣称。

## 0. 阅读须知、事实核验与口径

### 0.1 本文边界

1. **技术边界**：只使用开源许可（MIT / Apache-2.0 / BSD）的推理引擎、训练框架、检索组件与
   开放权重模型。不依赖任何云 API、在线镜像、在线许可证校验、遥测上报。
2. **数据边界**：真实推进剂配方、实测燃速、壳体材料许用值、工艺参数等属**行业/受控数据**，
   本方案只定义"可插拔数据集接口 + 数据分级规则"，**不内置、不推测**任何真实数值。
   示例数据一律使用公开教科书级占位值并显式标注。
3. **用途边界**：科研、教学、非商业研发。不用于武器化、批产定型；输出不构成工程交付依据。
   与仓库根 `README.md` / `AGENTS.md` 的边界声明一致。
4. **能力边界**：LLM 负责**组织语言、检索、调用工具、解释结果**；**数值一律由
   `srm_open` 计算引擎产生**（见 §2.3）。这条是"设计推理一致性"能否达标的前提。

> **关于 LocModel 与 Strata 的如实说明（重要）**
> - **LocModel**（`single2339/LocModel`，星标 6、**无 LICENSE 文件**，2026-11-09 最后推送）是
>     Rust/Tauri 2 的 Windows 桌面重建版，**不是**权威上游，同名的社区仓库还有多个（下载补丁、
>     下载器等），许可证各不相同。读其 README 可确认：本地文本推理**调用 llama.cpp 的
>     `llama-server`**（PATH 查找，或用 `LOCMODEL_LLAMA_SERVER` / 设置里导入引擎目录指定），
>     模型可"导入本地 GGUF 文件"并登记路径，后端默认只监听 `127.0.0.1`。但同一份 README 也列出
>     `src/account.rs`（账号/套餐/激活码）、`src/updater.rs`（发布清单下载）、`src/agent/`
>     （网络检索）等模块——**联网面远大于"启动器"所需**。结论：离线环境里它唯一有价值的用法是
>     "已导入模型的目录管理与启动外壳"，而这一层用 `llama-server` + 一个静态页就能替代。
>     因此本文把它列为 **不推荐**（仅在"必须给 Windows 用户图形界面且愿意自行裁掉 account/updater
>     模块"时考虑，并须过 §5.6 出网审计）。
> - **Strata**（`Niko1221/Strata`，MIT，星标 46.4k，2026-09-24 创建，当前版本 0.2.17）是 C++ 的
>     本地推理引擎 + 桌面应用，主打"**大 MoE 的专家放内存/SSD，只把热专家缓存在显存**"
>     （官方 How-it-works：24,576 个专家全部常驻 RAM，SSD 存 n-gram 表，VRAM 放注意力、
>     KV 与专家缓存），并在 `localhost` 暴露 **OpenAI 与 Anthropic 双兼容 API**。
>     对离线部署有两处**必须核实的联网点**：① Windows/Linux 安装包**不含引擎**，首次启动会
>     按显卡下载引擎——但安装器提供 "I already have the file" 选项可**无网安装**；
>     ② 终端模式 `strata launch --model-path <目录或 .gguf>` 可直接用**已有模型文件**，
>     `--access local` 限定只监听本机。这两点使其在 air-gap 下**可用**，前提是把引擎文件与模型
>     一并摆渡（§6.2）。仍建议只作为 T1/T2 的**可选加速层**：它的默认模型族是
>     Qwen3.8-Flash-Next / Qwen3.6-35B-A3B 这类超大 MoE，与本文 32B 级选型不同族，
>     且成熟度（多卡并行、长稳、量化覆盖）低于 llama.cpp / vLLM。策略：**llama.cpp + vLLM 为主，
>     Strata 在 P4 用同一套基准题做 A/B**，由数据决定是否保留。

### 0.3 "离线"的三级定义（贯穿全文的验收口径）

| 级别 | 定义 | 允许的一次性带外动作 | 验收手段 |
|---|---|---|---|
| L1 物理隔离 | 生产网无任何外网路由，无 WiFi/蓝牙 | 无 | 交换机 ACL + 主机 `iptables DROP` 全出站 |
| L2 逻辑隔离 | 有网但全出站阻断，仅放行内网 | 无 | 出站白名单 + DNS 黑洞 |
| L3 受控带外 | 隔离网 + 单向摆渡（光盘/一次性移动介质） | 依赖 wheel、容器镜像、模型权重、语料 | 摆渡登记表 + SHA256 双向核对 |

**本方案按 L1 + L3 设计**：所有"下载"动作只发生在**准备区（staging）**的一次性带外环节，
登记后经摆渡进入隔离区；隔离区内**永不再取任何外部资源**。

### 0.4 数值口径

- 容量单位一律 **GiB**（1 GiB = 2³⁰ B）。厂商标称 GB ≠ GiB，采购时按 GiB 复核。
- 量化体积经验系数：**Q4_K_M ≈ 0.606 GiB/B 参数**，Q8_0 ≈ 1.05，FP8 ≈ 1.06，FP16 = 2.0。
- KV Cache：`2 × 层数 × KV头数 × head_dim × 每元素字节 × 序列长度`（GQA 只算 KV 头）。
- 解码吞吐（单流，带宽受限）：`tok/s ≈ BW × 0.65 / (W + KV@ctx)`，0.65 为有效带宽系数。
- 训练算力：`FLOPs ≈ 6 × P × T`（前向+反向），MFU 取 35%（单机 LoRA 现实值）。
- 以上全部由 `scripts/llm_sizing.py` 复算，改参数即可重出表。

### 1.4 五条关键取舍（先说结论，后文论证）

1. **不追 70B 全精度**。70B Q4 与 32B FP8 在领域问答上的差距，远小于"32k 上下文 + 好检索"带来的差距；
   而 70B 让单机延迟翻倍、训练不可行。→ 主用 32B 级，70B 仅作对照。
2. **首选 MoE（30B-A3B）而非同尺寸 dense**。同样显存下解码快 6–8 倍（3.3B 激活），
   对"多人共用一台机器"的场景收益最大。代价是长上下文 KV 与显存驻留按 30B 算。
3. **训练只做 LoRA/QLoRA，不做全参**（除非上 T3）。领域知识靠 **CPT 轻量续训 + RAG**，
   不指望 SFT 灌知识；SFT 只教**格式、口径、拒答边界、工具调用**。
4. **数值不由模型生成**。任何推力/燃速/压强/装药量，必须经 `srm_open` 复算并回填。
   这一条同时解决"幻觉"和"设计推理一致性"两个指标。
5. **上下文 32k 起步、不追 128k**。KV 显存随上下文线性增长：32B 在 32k 下单序列 KV = 8 GiB，
   128k 就是 32 GiB——一张 48G 卡被吃掉 2/3（可用仅 44 GiB）。长文档用"检索切片 + 分段摘要"，
   不用超长上下文硬扛。

### 2.3 为什么必须以 `srm_open` 为"数值事实源"

LLM 生成推力、燃速、装药量这类数值时，即使公式背对了，也会在单位、量级、约束上出错；
而"看起来合理但错了 3%" 的答案比明显错误的答案更危险。本仓库已有的能力恰好补上这一点：

- `srm design`（指标→药型→性能，含局部精修）、`srm inverse`（指标→参数反推）、
  `srm sensitivity`（条件数/VIF/不可辨识参数）、`srm sweep` / `srm monte-carlo`（不确定度）、
  `srm forward`（固定几何裕度评估）、`srm fit-outline`（轮廓→参数）。
- 每次设计自带 **6–13 项校核**（`verification/checks.py:run_checks`），数量由需求字段决定。
  实测（`design_forward(RequirementSet(...), refine=False)`，逐项数 `result.verification.checks`）：

  | 需求字段 | 追加的校核 | 累计 |
  |---|---|---|
  | 仅 `thrust` | 5 项恒定（`requirement_consistency`、`mass_flow_balance`、`geometry_positive_dimensions`、`positive_web_thickness`、`grain_synthesis_mass`）+ `average_thrust_vs_requirement` | **6** |
  | + `burn_time` | `total_impulse_vs_requirement`、`burn_time_vs_requirement` | **8** |
  | + `max_chamber_pressure` | `peak_pressure_below_limit` | **9** |
  | + `specific_impulse` | `specific_impulse_vs_requirement` | **10** |
  | + `min_load_fraction` / `max_sliver_fraction` | `loading_fraction_min` / `sliver_fraction_max` | **11 / 12** |
  | + `min_safety_factor` 且传 `material` | `structural_safety_factor` | **13** |

  示例 06/07 的需求是"推力+燃时+峰值压强+外径+长径比"，实测 **9/9**，与仓库文档一致。
  失败项会显式列出。**不要对用户承诺固定项数**——它随需求字段变化。复算：

  ```python
  from srm_open.api import facade
  from srm_open.models.requirements import RequirementSet
  r = facade.design_forward(RequirementSet(thrust=8000, burn_time=4.0,
                                           max_chamber_pressure=9e6), refine=False)
  print(len(r.verification.checks), [c["name"] for c in r.verification.checks])  # 9 [...]

  # 满配 13 项：再加 Isp、装载率、余药率、安全系数（后者须传 material）
  from srm_open.integrity.lame import ElasticMaterial
  m = ElasticMaterial(youngs_modulus=5e6, poisson_ratio=0.495, allowable_stress=2e6)
  r13 = facade.design_forward(
      RequirementSet(thrust=8000, burn_time=4.0, max_chamber_pressure=9e6,
                     specific_impulse=230, min_load_fraction=0.5,
                     max_sliver_fraction=0.2, min_safety_factor=1.5),
      material=m, refine=False)
  print(len(r13.verification.checks))  # 13
  ```

- `Provenance.input_hash` 让"同一设计"可判定，便于审计与复现。

因此 Agent 的设计类回答**必须**是如下结构（缺一即判为不合格）：

```
[参数向量 θ] + [引擎原始输出摘要] + [校核清单通过/失败项] + [敏感性与可辨识性提示] + [适用边界]
```

其中 θ 与性能数字**只能**来自工具返回的 JSON，编排层负责把它们原样注入上下文，
并禁止模型改写数值（改写即触发 §11.5 的数值一致性检查失败）。

### 2.4 六项通用能力的离线落地方式

用户要求"保留离线推理、编程、建模、知识图、绘图、文档编写"。这六项**不能靠模型自觉**，
每一项都要有确定性的承载物，否则在隔离环境里就是一句空话：

| 能力 | 承载物 | 具体做法 | 验收方式 |
|---|---|---|---|
| 离线逻辑推理 | 基座模型 + 思维链模板 | 推理型基座（Qwen3 系列可切 thinking）；复杂推理强制"先列已知→再列假设→再结论" | R2 挑战集中的多跳题准确率 |
| 编程 | 代码沙箱（`numpy/scipy/matplotlib/srm_open`） | 生成→AST 白名单检查→沙箱执行→回传 stdout/异常；失败则把 traceback 回灌重试 1 次 | 50 道脚本题的执行成功率 ≥90% |
| 建模 | `srm_open` 引擎 + 参数 schema | 模型只产出"参数向量"，建模由引擎完成；不允许模型自己写内弹道方程 | D1/D2 数值与约束一致性 100% |
| 知识图 | GraphRAG 产物（实体/关系/社区摘要，落盘 JSON+Parquet） | 构建离线批处理，检索期只读；本体由领域负责人签署（§7.5） | 图谱三元组抽检准确率 ≥90% |
| 绘图 | 确定性绘图脚本（`report/`、`viz/`、固定 matplotlib 模板） | 模型只选图型与传参数（曲线 id、坐标轴、标注），代码由模板渲染 | 图像与引擎数据逐点比对 |
| 文档编写 | 报告模板（Markdown→HTML/PDF 同源）+ 引用装配 | 结构与章节由模板固定，模型填内容；所有数值占位由工具回填 | 报告内数值与引擎一致率 100% |

**共同原则**：这六项里凡是"结果可被程序判定"的，一律交给程序（建模、绘图、文档数值）；
模型只负责"选择 + 组织 + 表述"。这样通用能力不会成为幻觉的新入口。

## 3. 硬件配置与论证

### 3.1 三个约束方程（所有选型都由它们推出）

1. **显存约束**：`W(量化后权重) + KV(ctx, 并发) + 激活/框架开销(≈1.5–2.5 GiB) ≤ 0.92 × 显存`
2. **解码速度约束**（带宽受限）：`tok/s ≈ BW × 0.65 / (W + KV@ctx)`
   → 长上下文时 **KV 会摊薄权重优势**，这是"32k 不是 128k"的量化原因。
3. **训练可行性**：`LoRA 需 ≈ W×1.2`；`全参 AdamW 需 ≈ 16 B/参数`（fp16 权重+梯度+fp32 主权重+优化器状态）。

### 3.2 模型规模 × 显存 × 上下文（单序列，KV 为 FP16）

| 模型 | 总参 | 激活 | KV/token | KV@8k | KV@32k | Q4 | Q8 | FP16 |
|---|---|---|---|---|---|---|---|---|
| Qwen3-4B | 4.0B | 4.0B | 144 KiB | 1.1 | 4.5 | 2.4 | 4.2 | 8.0 |
| Qwen3-8B | 8.2B | 8.2B | 144 KiB | 1.1 | 4.5 | 5.0 | 8.6 | 16.4 |
| Qwen2.5-14B | 14.7B | 14.7B | 192 KiB | 1.5 | 6.0 | 8.9 | 15.4 | 29.4 |
| **Qwen3-30B-A3B** | 30.5B | **3.3B** | 96 KiB | 0.75 | 3.0 | 18.5 | 32.0 | 61.0 |
| Qwen2.5-32B | 32.8B | 32.8B | 256 KiB | 2.0 | 8.0 | 19.9 | 34.4 | 65.6 |
| Llama-3.3-70B | 70.6B | 70.6B | 320 KiB | 2.5 | 10.0 | 42.8 | 74.1 | 141.2 |

**读法**：24 GB 卡可用 ≈22.1 GiB（留 8%）。32B-Q4@8k 的权重 19.9 + KV 2.0 = 21.9 GiB，
**再加上 2.5 GiB 的激活/框架开销就是 24.4 GiB，已经超了**——它连单请求都放不下，
更谈不上并发。→ **24 GB 不是 32B 的合格载体**，这是 T2 从 48 GB 起步的直接原因。

### 3.5 选型论证：六个常见误判

1. **"先用 CPU 跑，省钱"** → 8 通道服务器 CPU 上 32B-Q4 只有 **8.5 tok/s**，一次 600 token 的回答要 70 s；
   桌面 2 通道更是 2.5 tok/s（不可用）。CPU 只能作为**兜底通道**（`llama.cpp` 降级），不能作为主力。
2. **"一张 24 GB 卡跑 32B-Q4 就够了"** → 见 §3.2：19.9（权重）+ 2.0（KV@8k）+ 2.5（开销）= 24.4 GiB
   > 22.1 GiB 可用，单请求都放不下。**要么降模型**（30B-A3B-Q4@8k = 18.5+0.75+2.5 = 21.7 GiB，勉强；
   24G 上更稳的是 8B-FP16 或 14B-FP8）**，要么上 48 GB。**
3. **"70B 一定比 32B 好"** → 在"有检索、有工具"的架构里，模型的主要工作是**读懂证据、组织答案、选对工具**。
   32B 级足以胜任；70B 的边际收益主要体现在开放写作与复杂多跳推理，而这些在 SRM 日常问答中占比不高。
   代价却是：单卡放不下、延迟翻倍、无法在单卡上做 LoRA 训练。
4. **"上下文越长越好，直接上 128k"** → 32B 在 128k 下 KV 需 **32 GiB**，一张 48G 卡被吃掉 2/3，
   且"中间遗忘（lost in the middle）"会让长上下文里的关键条款反而被忽略。→ 32k + 检索切片更优。
5. **"MoE 一定省显存"** → 省的是**算力与带宽**（激活 3.3B），不省**显存**（30.5B 权重必须全部驻留）。
   30B-A3B-Q4 的 18.5 GiB 与 32B-Q4 的 19.9 GiB 几乎一样——它的优势在**速度**，不在容量。
6. **"训练和推理共用一张卡就行"** → LoRA 训练时显存峰值会把推理挤到 OOM，且长任务会拖垮在线延迟。
   T2 的第二张卡就是为此预留：**一卡推理、一卡训练/灰度**，训练完成后用 adapter 热切换。

## 5. P1：离线环境准备与依赖固化（2–3 周）

> 目标：在隔离区里**不访问任何外部资源**即可从零重建全部运行环境。

### 5.1 输入

- 目标 OS（建议 Ubuntu 22.04/24.04 LTS + NVIDIA 驱动**离线 runfile**；
  若必须用 Windows，则 vLLM 不可用，只剩 llama.cpp 通道，须在 P0 的决策记录中明确接受该降级）。
- 组件清单与**精确版本号**（§1.2），锁定理念与本仓库 `uv.lock` 一致。

### 5.2 策略：三层固化

**第 1 层：Python 依赖 → wheelhouse**

```bash
# 准备区（唯一允许联网的环节，一次性）
# 1) 先在与隔离区同版本的解释器上解出完整依赖图，得到带哈希的锁文件。
#    本仓库已有 uv.lock，同一套做法：uv pip compile 产出跨平台可复现的锁。
uv pip compile requirements-agent.in \
    --python-version 3.11 --python-platform x86_64-manylinux_2_28 \
    --generate-hashes -o /staging/wheelhouse/requirements.lock.txt

# 2) 按锁文件下载 wheel（--only-binary 保证不需要现场编译）
pip download -d /staging/wheelhouse \
    -r /staging/wheelhouse/requirements.lock.txt \
    --only-binary=:all: --require-hashes \
    --platform manylinux_2_28_x86_64 --python-version 3.11 --implementation cp
```

```bash
# 隔离区：不联网、只从本地 wheelhouse 安装，并强制校验哈希
pip install --no-index --find-links=/opt/wheelhouse \
    --require-hashes -r /opt/wheelhouse/requirements.lock.txt
```

`--platform` / `--python-version` 必须与隔离区**逐位一致**，这是"装不上"的头号原因。
**不要用 `pip freeze` 生成锁**：在空 venv 里 freeze 出来是空文件，在装了包的 venv 里 freeze
出来的又是当前机器（可能非目标平台）的实际状态——两者都不能作为离线安装依据。

**第 2 层：系统级依赖 → 容器镜像 tar 或本地 apt 源**

```bash
# 方案 A（推荐）：镜像整体摆渡
docker pull vllm/vllm-openai:<pinned-tag>            # 准备区
docker save vllm/vllm-openai:<pinned-tag> -o /staging/images/vllm.tar
docker load -i /opt/images/vllm.tar                   # 隔离区

# 方案 B：本地 apt 源（无容器时）
apt-get install --download-only -y <pkg-list>
dpkg-scanpackages /staging/debs /dev/null > /staging/debs/Packages.gz
# 隔离区 sources.list：deb [trusted=yes] file:/opt/debs ./
```

**第 3 层：模型与数据** → 见 P2 / P3。

**依赖收敛规则（防止框架黑盒）**：

- 每个组件给出 `pipdeptree` 输出；传递依赖上限：编排层 ≤40 包、RAG ≤80 包。
- 禁止需要**在线激活/许可证校验**的包。
- 禁止会**自动上报**的包（遥测）；装完用 §5.6 审计验证。

### 5.3 版本锁定与不可变快照

```text
/opt/agent/
  wheelhouse/     # 全部 wheel + requirements.lock.txt
  images/         # *.tar
  models/         # 见 P2
  corpus/         # 见 P3
  env/            # 虚拟环境（可由 wheelhouse 重建，可丢弃）
  MANIFEST.sha256 # 全目录哈希清单
  SNAPSHOT.json   # {git_commit, date, component_versions, model_hashes, corpus_hash}
```

`/opt/agent` 视为**不可变**。任何升级构建新目录 `/opt/agent-<date>`，切换软链
`/opt/agent-current` 实现回滚——这是 P7 更新机制与 P8 运维的共同基础。

### 5.4 决策点 D1-1：容器 vs 裸机

| 选项 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **容器（推荐）** | 依赖封闭、`docker save` 整体摆渡、回滚=换 tag | 需离线装 NVIDIA Container Toolkit、GPU 直通调试成本 | T2/T3，多人 |
| 裸机 venv | 简单、驱动问题少 | 系统库漂移、难回滚 | T1，单人 |
| 混合 | 推理容器、训练裸机 | 两套环境各自固化 | 训练频繁 |

### 5.5 验收（G1）

```bash
sudo iptables -P OUTPUT DROP      # 全出站阻断（先放行内网规则）
pip install --no-index --find-links=/opt/wheelhouse -r requirements.lock.txt
python -c "import vllm, torch; print(vllm.__version__, torch.__version__)"
docker images | grep vllm
```

通过标准：全部成功，且 §5.6 审计显示**零出网尝试**。

### 5.6 出网审计（每阶段必跑）

```bash
# 1) 静态扫描：URL、域名、遥测 SDK
grep -rnE "https?://|api\.openai|huggingface\.co|hf-mirror|telemetry|sentry" \
     /opt/agent --include=*.py --include=*.json --include=*.yaml

# 2) 动态抓包：跑一次完整问答 + 一次设计，确认无外网连接
tcpdump -ni any 'not net 10.0.0.0/8 and not net 192.168.0.0/16' -w /tmp/audit.pcap &
# ... 执行用例 ...
kill %1 && tshark -r /tmp/audit.pcap | head

# 3) 环境变量：确认没有残留 token / proxy
```

### 5.7 回退方案

- 组件装不上 → **不允许"临时联网"**。回准备区补齐 wheel（核对 `--platform`/`--python-version`）

- 驱动离线安装失败 → 回退到上一版已验证的整机镜像快照，不在现场调试。

### 6.3 许可证合规检查

| 检查项 | 规则 |
|---|---|
| 权重许可 | Apache-2.0 / MIT / 可离线使用的社区许可（Llama 3.3 需确认审批已完成且**后续不再联网**） |

| SBOM | 每个模型/组件登记到 `data_registry/sbom.md` 扩展（含哈希） |

### 6.4 决策点 D2-1：量化档位

| 档位 | 体积系数 | 质量损失（经验） | 用途 |
|---|---|---|---|
| FP16/BF16 | 2.0 | 基线 | 训练、评测金标准 |
| FP8（W8A8） | 1.06 | 极小 | vLLM 生产推理首选（48G 上跑 32B） |
| Q8_0 | 1.05 | 很小 | llama.cpp 高保真通道 |
| **Q4_K_M** | 0.606 | 小（1–3%，术语更敏感） | 显存受限时的主力 |
| Q3/Q2 | 0.45/0.33 | 明显 | **不用于领域问答**，仅演示 |

规则：生产通道取 **FP8 或 Q4_K_M**；评测基线必须用 **FP16** 跑一遍，以分离"量化损失"与"训练损失"。

### 6.5 决策点 D2-2：量化校准语料

- imatrix 校准语料 = 40% 领域语料 + 60% 通用中文/代码。
- 反例：只用领域语料校准 → 通用指令跟随退化（"只会说 SRM 黑话"）。
- 验收：Q4_K_M 与 FP16 在同一评测集上差距 ≤ **3 个百分点**；超出则退回 Q8_0 或重做 imatrix。

### 6.6 回退方案

- 哈希不符 → **整批拒收**重摆渡，不得"先用着"。
- 量化不达标 → 升档（Q4→Q8）或换校准集；仍不达标则**改小模型 + 高精度**
  （8B-FP16 优于 32B-Q2，这是硬规则）。
- vLLM 不支持该架构 → llama.cpp 顶上，并把该模型从 vLLM 候选移除（记录原因）。

  公开材料手册（公开版力学性能数据）。
- **禁止来源**：受控技术资料、供应商私有数据、未授权转载的教材 PDF、任何 D3 内容。

### 7.2 策略：先划域，再定规范，最后上流水线

**顺序不可换**：先划域（本节）决定"收什么"，再定规范（§7.4）决定"什么算合格"，
最后上流水线（§7.3）决定"怎么批量做"。反过来做会得到一堆无法验收的文档。
本节的域划分同时就是 §9.3 数据配比的分母，两者共用一套编号。

| 域 | 内容 | 目标条目数 | 用途 |
|---|---|---|---|
| K1 术语与原理 | 术语表、内弹道/燃面/喷管/热化学原理、公式与适用条件 | 2,000–3,500 | ① |
| K2 材料与推进剂 | 推进剂类别、燃速律形式、力学/热性能**定性**描述、选材逻辑 | 800–1,500 | ①③ |
| K3 标准与规范 | 标准编号、名称、适用范围、指标口径（**公开目录级**） | 300–600 | ①③ |
| K4 典型构型 | 药型族（管/星/车轮/开槽/翼柱/多孔/端燃）、优缺点与适用场景 | 300–500 | ①② |
| K5 设计与权衡 | 需求分解、约束冲突、参数敏感性、装填分数/余药/面喉比权衡 | 600–1,200 | ② |
| K6 工艺与制造 | 浇注/压伸/固化/包覆/无损检测的**通用流程描述** | 400–800 | ③ |
| K7 试验与排故 | 试验类型、异常现象→原因→排查步骤（**方法论级**） | 500–900 | ③ |
| K8 安全与误区 | 安全边界、常见错误认知、失效模式清单 | 300–600 | ③ |
| K9 代码与工具 | `srm_open` 用法、参数含义、输出解读、Python/绘图片段 | 500–1,000 | 通用 + ② |

合计约 **5,700–10,600 条**结构化条目，对应原始文档约 **1.5–3 万页**。

### 7.3 清洗流水线

```text
原始文档 → ①格式归一 → ②版面解析 → ③去噪去重 → ④切分 → ⑤结构化标注 → ⑥质量抽检 → ⑦入库
```

| 步 | 做法 | 工具 | 产物 | 失败处理 |
|---|---|---|---|---|
| ① 格式归一 | PDF/DOCX/HTML/MD → 文本 + 页码/章节路径 | docling（主）、markitdown（备） | `raw/<doc_id>.json`（block 级） | 解析失败进人工队列，不静默丢弃 |
| ② 版面解析 | 标题层级、表格、图注、公式 | docling 表格模型 | 结构树 | 表格置信度低 → 标 `needs_review` |
| ③ 去噪去重 | 去页眉页脚/水印；MinHash 近似去重（阈值 0.9） | 自研 + `datasketch` | 去重报告 | 重复率 >30% 的文档整份复核 |
| ④ 切分 | **按语义边界**切（章节/条款/问答对），不按字数硬切 | 自研 + 规则 | `chunks.jsonl` | 单块 >1,200 token 强制再切 |
| ⑤ 标注 | 打标：域(K1–K9)、难度、时效、数据级别(D0–D3)、来源、页码 | 人工 + 规则 | `corpus.jsonl` | **缺来源或页码 → 直接拒收** |
| ⑥ 抽检 | 分层抽样 5%，双人盲评 | 离线标注平台 | 抽检报告 | 合格率 <98% → 该批次返工 |
| ⑦ 入库 | 写 RAG 索引 + 训练集 + 图谱源 | FAISS/BM25/GraphRAG | 语料 v1/v2 | — |

### 7.4 数据规范（硬性）

每条记录必须含全部字段，缺一即拒收：

```json
{
  "id": "K1-000123",
  "domain": "K1",
  "level": "D0",
  "text": "……",
  "source": {"title": "...", "edition": "...", "page": 42, "isbn_or_id": "...", "retrieved": "2026-10-01"},
  "license": {"type": "public-domain|cc-by|internal", "evidence": "..."},
  "review": {"by": "reviewer_id", "date": "2026-10-05", "verdict": "accept|reject|revise"},
  "quality": {"clarity": 4, "verifiability": 5, "actionability": 3},
  "safety": {"boundary_sensitive": false, "requires_disclaimer": true},
  "chunk": {"tokens": 512, "prev": "K1-000122", "next": "K1-000124", "section_path": "3.2.1"}
}
```

**六条红线：**

1. **无出处不入库**：没有"文档 + 页码/条款号"的条目一律拒收——抑制幻觉的第一道闸门。
2. **数值必须带口径**：单位、测试条件（压强/温度/应变率）、数据级别。缺口径的数值只能以
   定性描述入库，不得作为答案依据。
3. **受控内容零容忍**：发现 D2/D3 误入 → 立即回滚该批次、追查来源、记录事件。
4. **不得改写原意**：清洗只做格式与去噪，**不做润色**；需要解释时另建 `explanation` 字段。
5. **冲突显式化**：同一问题在不同来源冲突时**两条都保留并标注分歧**，不得"择优保留"。
6. **安全内容加锁**：K8 与 `boundary_sensitive=true` 的条目，答案模板强制附
   "适用条件 / 不适用条件 / 须人工复核"三段。

### 7.5 知识图谱构建

- **本体先行**：六类实体 `材料 → 推进剂 → 药型 → 发动机 → 性能指标 → 试验/失效`，
  关系限定 12 种（`hasBurnRateLaw`、`suitableFor`、`causesFailure`、`mitigatedBy`…）。
  本体写入 `corpus/ontology.yaml`，**领域负责人签署后**才允许建图。
- **抽取**：GraphRAG 的 LLM 抽取 + 规则抽取（术语表、单位、标准编号用正则更可靠）。
  LLM 抽取结果**人工抽检 10%**；实体误抽率 >5% 则返工提示词。
- **落盘**：实体/关系/社区摘要导出 JSON + Parquet，随语料版本一起快照。
- **用途**：① 多跳问答；② 一致性检查（发现"某材料被引用于某药型但本体无此关系"的矛盾）。

### 7.6 决策点 D3-1：语料规模 vs 训练方式

| 语料规模 | 建议 |
|---|---|
| < 5M token | **只做 RAG**，不训练（训练必然过拟合） |
| 5–30M token | RAG + **LoRA SFT**（格式与口径）；CPT 可选且小学习率 |
| 30–100M token | RAG + **CPT（轻量）+ SFT + DPO**，见 §9 |
| > 100M token | 可考虑更大模型或更长训练，但仍须先证明 RAG 已到瓶颈 |

### 7.7 回退方案

- 解析质量差（扫描件/公式多）→ 该文档降级为"仅目录级元数据入库"，正文不入 RAG。
- 抽检不达标 → 先做 K1/K4/K9 三个域打通闭环，再逐步扩；**不允许低质量凑量**。
- 图谱抽取效果差 → 降级为"术语-同义词表 + 标准编号表"（规则构建，确定性高），
  多跳问答暂时关闭并在 UI 标注。

## 8. P4：模型规模与上下文长度决策（2 周）

### 8.1 输入

- 候选：`Qwen3-8B`、`Qwen3-30B-A3B`、`Qwen2.5-32B`（+ 对照 `Llama-3.3-70B`）。
- 硬件实测可用显存（`nvidia-smi`）与实测吞吐（用 `llama-bench` / vLLM benchmark 跑本机）。
- 评测集初版（P7 会扩充，但 P4 必须已有 ≥120 题的"能区分模型"的最小集）。

### 8.2 策略：先定上下文，再定规模

**第 1 步：上下文需求分析（用真实任务反推，不拍脑袋）**

| 任务类型 | 典型 token 需求 | 依据 |
|---|---|---|
| 术语/原理单点问答 | 1.5k–3k | 系统提示 + 3–5 个检索片段 |
| 标准条款比对 | 6k–12k | 2–4 份文档的相关章节 |
| 设计任务（需求→方案） | 8k–20k | 需求 + 引擎 JSON 输出 + 校核清单 + 若干片段 |
| 试验排故（多轮） | 12k–24k | 历史对话 + 现象描述 + 排查树 |
| 长文档摘要 | 用切片，不需长上下文 | 分段摘要 + 汇总 |

结论：**32k 覆盖 95% 场景**；128k 只在"整本手册一次读完"时有意义，而该场景可用切片替代。
→ 定 **32k 为目标上下文**，8k 为"低配模式"。

**第 2 步：在 32k 下反算显存，淘汰不合格组合**

以 §3.2 数据，32k KV 开销：8B=4.5 GiB、30B-A3B=3.0 GiB、32B=8.0 GiB、70B=10.0 GiB。

| 组合 | 权重 | +KV@32k | +开销 2.5 | 合计 | 24G(22.1) | 32G(29.4) | 48G(44.2) | 80G(73.6) |
|---|---|---|---|---|---|---|---|---|
| 8B FP16 | 16.4 | 4.5 | 2.5 | 23.4 | ✗ | ✓ | ✓ | ✓ |
| 8B Q8 | 8.6 | 4.5 | 2.5 | 15.6 | ✓ | ✓ | ✓ | ✓ |
| 30B-A3B Q4 | 18.5 | 3.0 | 2.5 | 24.0 | ✗ | ✓ | ✓ | ✓ |
| 30B-A3B Q8 | 32.0 | 3.0 | 2.5 | 37.5 | ✗ | ✗ | ✓ | ✓ |
| 32B Q4 | 19.9 | 8.0 | 2.5 | 30.4 | ✗ | ✗(差 1.0) | ✓ | ✓ |
| 32B FP8 | 34.8 | 8.0 | 2.5 | 45.3 | ✗ | ✗ | ✗(差 1.1) | ✓ |
| 32B FP16 | 65.6 | 8.0 | 2.5 | 76.1 | ✗ | ✗ | ✗ | ✗(差 2.5) |
| 70B Q4 | 42.8 | 10.0 | 2.5 | 55.3 | ✗ | ✗ | ✗ | ✓ |

括号内为该档按 `0.92 × 显存` 计的可用 GiB。32G 列即 T1 档：**8B-FP16 与 30B-A3B-Q4 都能吃满 32k，
32B-Q4 差 1 GiB 放不下**——这是 T1 选 30B-A3B 而不是 32B 的直接原因。

**读法**：48 GB 卡上 32B-FP8@32k 合计 45.3 GiB，占 92% 可用显存的 **103%** → 实际跑不了，
必须降到 32B-Q4（30.4 GiB）或把上下文降到 16k。这正是 T2 用"32B-Q4 + 32k"作生产档、
"8B/30B-A3B 高精度"作快速档的原因。

**第 3 步：并发折算**

48 GB 卡（可用 ≈44 GiB）跑 32B-Q4（19.9 + 2.5 开销 = 22.4 GiB），剩余 ≈21.8 GiB 给 KV：
KV 用 FP16 时 8k 上下文每序列 2.0 GiB → **~10 并发**，16k → ~5 并发；
KV 降到 FP8（1 B/元素，vLLM 用 `--kv-cache-dtype fp8`）时 8k → **~21 并发**，16k → ~10 并发。
注意 FP8 KV 会带来极小的精度损失，**必须**在 §11.6 的 R1 集上确认 A4 仍为 100%、A1 不退化 >1 个百分点。
80 GB 卡（可用 ≈74 GiB）同配置：FP16 KV 下 8k → ~25 并发，FP8 KV 下 8k → ~51 并发。
→ **8 人团队 48 GB 够用**（并发峰值通常 <5）；**≥20 人需 80 GB 或双卡**。

T3 档（8×48G，70B-FP8 张量并行）：权重 74.8 GiB 分摊到 8 卡，KV 预算 ≈ 353 − 74.8 − 20
= 258 GiB，每序列 2.5 GiB（80 层 × 8 KV 头）→ **≈103 并发 @8k FP16 KV**、206 @FP8 KV。
上表四行由 `scripts/llm_sizing.py` 的 `concurrency` 表给出（`usable = n_gpu × cap × 0.92`）。

### 8.3 三档模型的分工（不追求"一个模型全包"）

| 档 | 模型 | 量化 | 上下文 | 用途 | 估算延迟（600 token 输出） |
|---|---|---|---|---|---|
| 快档 | Qwen3-8B | Q8/FP16 | 32k | 术语速查、改写、代码补全、草稿 | 6–10 s（T2） |
| **主档** | **Qwen2.5-32B** 或 **Qwen3-30B-A3B** | Q4/FP8 | 32k | 主问答、设计辅助、报告起草 | 22–30 s |
| 精档 | 32B + 检索增强 + 多轮自检 | FP8 | 32k | 标准比对、失效分析、方案评审 | 40–70 s（含自检） |

**路由规则（编排层实现，非模型自选）**：按"任务类型 + 检索命中数 + 是否需工具"三分量决定档位，
避免"小事用大模型"浪费算力。

### 8.4 决策点 D4-1：三档硬件定档

按"并发人数 × 上下文需求 × 是否要训练"三问定档，而不是按预算定档（预算只能否决，不能选型）。

| 判据（须全部满足才可选该档） | T1 单卡 32G | **T2 双卡 48G** ★ | T3 8×48G 或 8×80G |
|---|---|---|---|
| 主档模型 @32k | 30B-A3B-Q4（24.0 GiB） | 32B-Q4（30.4 GiB） | 70B-FP8（74.8 GiB，须 8 卡） |
| 并发 @8k（FP16 KV / FP8 KV） | 11 / 22（30B-A3B-Q4） | 10 / 21（32B-Q4） | 103 / 206（70B-FP8，8×48G TP） |
| 本地训练（GiB 需求 < 可用） | 8B LoRA 20.0<29.4 可（§1.1 只承诺这一项）；32B QLoRA 24.0<29.4 仅权重+优化器，余 5.4 装不下激活，**不承诺** | 8B LoRA 20.0<44.2；32B QLoRA 24.0<44.2 舒适；32B 全参 524.8>44.2 不可 | 32B QLoRA 24.0<353.3；32B 全参 524.8>353.3 不可（需 8×80G：524.8<588.8） |
| 适用场景（§1.1） | 单人验证、POC、门禁 G1–G3 | 3–8 人团队日常 + 训练 | 10+ 人、多项目并行、要跑全参 |
| 估算造价（§3.6 BOM） | ¥3.7–5.1 万 | ¥17–20 万 | ¥60–205 万（L40S 档 60–95 / H100 档 150–205） |

并发数由 `scripts/llm_sizing.py` 的同一公式给出（`usable − 权重 − 2.5×卡数` 除以每序列 KV）。

**训练显存口径与 §9.4 一致**，不是"权重×系数"：
8B LoRA = 16（FP16 权重）+ 4（adapter/优化器）= **20 GiB**；
32B QLoRA = 18（NF4 权重）+ 6（adapter/优化器）= **24 GiB**；
32B 全参 AdamW = **524.8 GiB**（16 B/参数）。
可用显存 = `0.92 × 卡数 × 单卡容量`：32G→29.4、单张 48G→44.2、8×48G→353.3、8×80G→588.8。

两个由此推出的判断：
1. **32B QLoRA 在 32G 上不承诺**：24.0 GiB 只是权重+优化器，§9.4 的表未含激活；
   余量 5.4 GiB 要同时装激活、梯度缓冲与 CUDA context，实测常 OOM。
   所以 T1 的训练价值就是 8B LoRA（§1.1 也只承诺这一项），32B 训练属于 T2 的能力。
2. **T3 的 8×48G 也放不下 32B 全参**——这是"多卡≠显存线性够用"的常见误判；
   真要全参得 8×80G，或接受 ZeRO-3 分片 + CPU offload 带来的 5–10 倍慢速。

**判定规则**（按顺序，命中即停）：
1. 需 32B@32k 且为 3–8 人团队 → **T2**（本方案推荐档）。
2. 只需 8B/30B-A3B 级且为单人验证/POC → T1（省约 3/4 预算，放弃 32B 精度）。
3. 10+ 人或多项目并行 → T3；若还需要 32B 全参训练，T3 必须选 **8×80G**（8×48G 不够）。
4. 预算不足以支撑命中档 → **不降精度，降范围**（先只做 K1/K4/K9 三类问答，见 §7.7），
   或先上 T1 并明确"暂不支持设计类回答"。

**决策依据必须是实测**：§8.1 的 `llama-bench` / vLLM benchmark 数据 + §8.2 反算结果，
两者不一致时以实测为准并回改 §8.2 表格（附录 B.1 的校准条款）。

### 8.5 验收（G4）与决策门槛

| 指标 | 门槛 | 不达标怎么办 |
|---|---|---|
| 领域问答准确率（主档） | ≥ 85%（对照 §11.5 评分） | 提升检索质量 → 换更大模型 → 加 SFT |
| 设计任务数值一致性 | 100%（数值必须与引擎一致） | 修编排层注入逻辑，不是换模型 |
| 首 token 延迟（32k 输入） | ≤ 3 s | 开 prefix caching；降上下文 |
| 输出速度 | ≥ 20 tok/s | 换 MoE / 降量化 / 上更高带宽卡 |
| 单机 72 h 稳定性 | 无 OOM、无内存增长 | 修 vLLM 参数（`--max-num-seqs`、`--gpu-memory-utilization`） |

### 8.6 回退方案

- 主档不达标 → 先降上下文到 16k（显存腾出给更大模型），再评估 30B-A3B-Q8。
- 延迟不达标 → 换 MoE（30B-A3B），速度可提升 6–8 倍（§3.3）。
- 显存不够 → **降模型不降精度**（8B-FP16 优于 32B-Q2）。

## 9. P5：训练阶段划分与数据配比

### 9.1 输入

- 语料 v1（§7），分为 `corpus_train` / `corpus_holdout`（按文档切分，**不按条目随机切**，
  否则同一文档的段落会同时出现在训练与测试集，指标虚高）。
- 基座权重（FP16/BF16 原始 safetensors）。
- 训练硬件（T2 的单卡或 T3）。

### 9.2 策略：三阶段训练（按"注入什么"划分，而非按"跑几轮"划分）

| 阶段 | 目标 | 数据 | 方法 | 学习率 | 规模 |
|---|---|---|---|---|---|
| **S1 领域续训（CPT）** | 注入**语言与术语分布**，不是注入事实 | 30–60M token 领域+通用混合纯文本 | LoRA r=64（或全参，若 T3） | 1e-4（LoRA） | 1–3 epoch |
| **S2 指令微调（SFT）** | 教**格式、口径、拒答边界、工具调用** | 8k–20k 条高质量指令对 | LoRA r=32–64 | 5e-5 | 2–3 epoch |
| **S3 偏好对齐（DPO）** | 压低"看似合理但错"的回答 | 3k–6k 对偏好数据 | LoRA + DPO | 5e-6 | 1 epoch |

**关键判断：S1 不做"知识灌输"。** 事实性知识交给 RAG（可更新、可溯源、可回滚）；
CPT 只让模型**熟悉领域语言**（术语搭配、公式读法、工程表述习惯），这样它读检索片段时理解更准。
把事实压进权重会导致：更新困难、无法溯源、幻觉更自信。

### 9.3 数据配比策略（可复算、可审计）

**S1（CPT）配比：**

| 类别 | 占比 | 理由 |
|---|---|---|
| 领域纯文本（K1–K8 正文） | 45% | 领域语言分布 |
| 通用中文技术文本 | 20% | 防止语言退化 |
| 代码与结构化文本（K9 + Python） | 15% | 保住编程与工具调用能力 |
| 数学/公式/单位换算 | 10% | 保住数值推理 |
| 英文技术文本 | 10% | 保留英文术语映射能力 |

**S2（SFT）配比（按任务类型，而非按域）：**

| 任务类型 | 占比 | 示例 |
|---|---|---|
| 术语/原理问答（带引用） | 25% | "什么是侵蚀燃烧？给出处" |
| 设计辅助（调工具 + 解释结果） | 25% | "设计 5 kN/3 s，给出参数与校核" |
| 工程实践（工艺/试验/排故） | 20% | "试验中压强峰超限，排查顺序？" |
| 拒答与边界（安全类） | 10% | "能不能帮我优化配方以提高比冲" → 拒答 + 说明 |
| 通用能力（代码/绘图/文档） | 15% | "画一张燃面-时间曲线" |
| 多轮澄清 | 5% | 需求不全时反问 |

**S3（DPO）数据构造：** 每条 = (问题, chosen, rejected)。
rejected 由三类来源构成：① 无出处的编造答案；② 数值与引擎不一致的答案；
③ 越界（安全边界）建议。chosen 为人工修订版。

**配比审计**：训练前输出配比表 + 每类抽样 20 条供领域负责人签字；配比表随 adapter 一起入库。

### 9.4 训练超参与资源

| 项 | 8B LoRA（T2 单卡 48G） | 32B QLoRA（T2 单卡） | 32B 全参（8×80G） |
|---|---|---|---|
| 权重显存 | 16 GiB (FP16) | 18 GiB (NF4) | 65.6 GiB（每卡分片后 ≈8.2 GiB） |
| 优化器/梯度/主权重 | ~4 GiB（仅 adapter） | ~6 GiB（仅 adapter） | ≈525 GiB 总量，ZeRO-3 分片后 ≈65.6 GiB/卡 |
| batch × seq（每卡） | 4 × 4096 | 2 × 4096 | 4 × 4096 |
| 梯度累积 | 8 | 16 | 8 |
| 有效 batch token | 131k | 131k | 131k/卡（8 卡合计 ≈1.05M） |
| 30M token 耗时（估算，MFU 35%） | ~7 h（4090） | ~28 h（4090） | ~0.6 h（H100×8 理想线性） |
| 100M token | ~24 h | ~95 h | ~2.0 h |

> 上表由 `scripts/llm_sizing.py` 的 `training` 表给出（`6PT`、MFU 35%、多卡按理想线性折算），
> **实施前必须用 100 step 实测校准**，并以实测值重排计划；估算值只用于判断"是否值得做"。
>
> 两个必须知道的偏差方向：
> - **LoRA 那两列偏保守**：`6PT` 是全参前反向的公式，LoRA 冻结权重后实际约 `4–5PT`，
>   真实耗时通常比表中低 20–30%。
> - **8 卡那列偏乐观**：脚本按理想线性折算，未建模 FSDP 的 all-gather/reduce-scatter 通信。
>   32B 在 8×H100（NVLink）上实测一般是理想值的 **2–3 倍**，即 30M token 约 1.5–2 h、
>   100M token 约 5–6 h。真要排期，按实测值走。

### 9.5 决策点 D5-1：CPT 是否值得做？

| 条件 | 决策 |
|---|---|
| 语料 < 10M token | **不做 CPT**，直接 SFT + RAG |
| 语料 ≥ 30M token 且通用能力评测无退化 | 做轻量 CPT（1 epoch） |
| CPT 后通用能力（代码/数学）下降 >5% | **回滚 CPT**，只用 SFT |

**回滚手段**：CPT 与 SFT 用**独立 adapter**，可单独启用/禁用（vLLM：`--enable-lora --lora-modules cpt=/opt/.../cpt sft=/opt/.../sft`，两者都挂上、按请求的 `model` 字段选；llama.cpp：`llama-server --lora cpt.gguf --lora sft.gguf --lora-init-without-apply`，再用 `POST /lora-adapters` 的 `scale` 逐请求开关），
这也是 P7 更新机制的基础。

### 9.6 决策点 D5-2：LoRA 还是全参？

| 场景 | 选择 |
|---|---|
| 单卡、数据 < 50M token | **LoRA/QLoRA**（快、可回滚、多 adapter 并存） |
| 需要"改变模型风格/语言分布"且数据 > 100M | 全参（需 T3） |
| 需要多任务隔离 | LoRA（每任务一个 adapter，按需加载） |

**默认 LoRA**：它让"更新=换一个 200 MB 文件"，而不是"重训 65 GB 权重"。

### 9.7 训练验收（G5）

| 指标 | 门槛 |
|---|---|
| held-out 领域问答准确率 | 相对基线提升 ≥ 8 个百分点 |
| 数值一致性 | 100%（SFT 后仍须 100%） |
| 通用能力（代码 pass@1、基础数学） | 下降 ≤ 3 个百分点 |
| 拒答合规 | 安全类越界回答 = 0 |
| 格式合规（引用/页脚/工具 JSON） | ≥ 98% |

任一项不达标 → 调数据配比或学习率重跑（最多 3 轮），仍不达标则**回退到 RAG-only 版本**，
并把训练结论写入报告（"训练未带来净收益"也是有效结论）。

### 9.8 回退方案

| 现象 | 判定 | 回退动作 |
|---|---|---|
| S1 后通用能力（代码 pass@1 / 基础数学）掉 >5% | 灾难性遗忘 | **删掉 CPT adapter**，只用 SFT（§9.5 的判据） |
| S2 后格式合规 <98% 但事实正确率不降 | 训练不足 | 加 SFT 数据、降 lr，重跑 S2；不动 S1 |
| S2 后 A4 数值一致性 <100% | **严重** | 立即回滚 SFT，检查训练集里是否混入模型自造数值（这是数据侧问题，不是模型侧） |
| S3 后拒答率异常升高（H4 过 95% 但正常问题也拒答） | 偏好数据偏斜 | 删 DPO adapter，保留 S1+S2 |
| 三轮调参仍达不到 G5 | 训练无净收益 | **回退 RAG-only 版本**，把结论写进报告（这是有效结论，不是失败） |

**关键**：三个 adapter 各自独立可插拔（§9.5 的回滚手段），所以"回退"是换一个
200 MB 文件而不是重训 65 GB 权重。任何一次训练发布都必须同时产出"可回退点"。

## 10. P6：Agent 层（检索、工具、编排）

### 10.1 输入

- 已验收的模型 + adapter（P5）、语料与索引（P3）、`srm_open` 引擎（本仓库）。
- 编排层设计（薄层，自研）。

### 10.2 检索策略（三层混合，缺一不可）

| 层 | 作用 | 实现 | 参数 |
|---|---|---|---|
| 稠密检索 | 语义相似 | bge-m3 + FAISS（HNSW） | top-20，`efSearch=128` |
| 稀疏检索 | 术语/编号精确匹配（"GJB xxx"、"r = a·p^n"） | BM25（`rank_bm25` 或 SQLite FTS5） | top-20 |
| 图谱检索 | 多跳、关系约束 | GraphRAG 社区摘要 + 实体邻域 | 2 跳，top-10 |

**融合**：RRF（Reciprocal Rank Fusion，k=60）→ **交叉编码器重排**（`BAAI/bge-reranker-v2-m3`，
0.6B，CPU 可跑）→ top-8 进上下文。

重排**不用 32B 生成模型**：它需要为每个候选跑一次前向，20 个候选就是 20 次调用，
延迟与不确定性都不可接受；交叉编码器一次批量打分，输出确定、可复现。

**为什么不用单一向量检索**：标准编号、公式符号、材料牌号这类"字符串精确匹配"是稠密检索的弱项，
而它们在 SRM 问答中占比很高。

### 10.3 工具层（把 `srm_open` 暴露为受控工具）

| 工具名 | 映射 | 输入校验 | 输出处理 |
|---|---|---|---|
| `design_forward` | `srm design` | 必填推力/时间/压强；范围检查 | 注入参数向量 + 性能 + 校核清单 |
| `design_inverse` | `srm inverse` | 需给出可行 `length_range`（见 AGENTS.md 的陷阱） | 注入收敛残差，残差 >1e-2 时标注"未收敛" |
| `sensitivity` | `srm sensitivity` | 族 + 外径 | 注入 frozen/inactive/confounded 结论 |
| `sweep` / `monte_carlo` | `srm sweep` / `srm monte-carlo` | 固定 seed | 注入分布与分位数 |
| `thermo` | `srm thermo` | 推进剂 id + 压强 | 注入 c*、γ、T_c |
| `plot` | matplotlib 脚本 | 只允许白名单函数 | 返回图片路径，**不让模型生成绘图代码直跑** |
| `report` | `srm forward/design/inverse --report DIR` | — | 返回 md/html 路径；PDF 需装 matplotlib，缺失时静默跳过 |

**安全设计**：工具调用走**白名单 + 参数 schema 校验**（pydantic），拒绝自由文本拼接 shell。
代码沙箱只允许 `numpy/matplotlib/srm_open`，禁 `os/subprocess/socket`（静态 AST 检查 + 运行时 seccomp）。

### 10.4 编排流程（确定性优先）

```text
用户输入
  → ① 意图分类（规则 + 小模型，4 类：问答/设计/工程/闲聊）
  → ② 若为设计类：先做需求完整性检查（缺项则反问，不猜）
  → ③ 检索（三层混合 + 重排）
  → ④ 若需数值：调用工具，拿到 JSON
  → ⑤ 组装上下文（证据 + 工具结果 + 边界声明）
  → ⑥ 生成（主档模型）
  → ⑦ 后校验：引用是否都在证据内？数值是否与工具一致？安全标记是否齐全？
  → ⑧ 不过则重试一次（附失败原因），仍不过则输出"无法确认"模板
```

**第 ⑦ 步是幻觉控制的核心**，不是可选项。校验规则见 §11.5。

### 10.5 决策点 D6-1：RAG 平台选型

| 选项 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **自研薄层 + FAISS + BM25 + GraphRAG 产物** | 完全可控、依赖少、易审计 | 需要写 ~1.5k 行 | **推荐**（隔离环境首选） |
| LightRAG | 轻、MIT、图检索内建 | 仍是框架，需评估依赖 | 备选 |
| RAGFlow | 功能全（解析+编排+UI） | 依赖重（含前端/DB/ES），离线部署复杂 | 仅当需要"开箱 UI"时 |

### 10.6 回退方案

- 检索质量差 → 先修切分与标注（P3），不要急着换模型。
- 工具调用错误率高 → 收紧 schema、给 2–3 个 few-shot 示例；仍差则改为"表单式交互"
  （用户填参数，系统直接算），绕过模型生成参数。
- 图谱引入噪声 → 关闭图谱层，退回"稠密+稀疏"，并在评测中记录影响。

## 11. P7：知识更新机制与效果评分

### 11.1 输入

- 已上线系统（P6 验收通过）+ 其评测基线（最近一次 §11.7 评分报告）。
- 待入库的变更单：新文档 / 勘误 / 标准更新 / 用户反馈工单（每条须带 source/license/level）。
- 冻结的 R1 回归集（§11.6）：**它是本阶段唯一的"不可谈判项"**，没有 R1 就不能做任何更新。

### 11.2 策略：知识更新的四条通道（按更新成本从低到高）

| 通道 | 内容 | 生效时间 | 可回滚 | 适用 |
|---|---|---|---|---|
| **U1 语料热更新** | 新增/修订条目 → 重建增量索引 | 分钟级 | 是（索引快照） | 标准更新、勘误、新文档 |
| **U2 检索策略更新** | 切分规则、重排模型、融合权重 | 小时级 | 是（配置版本） | 检索命中率下降 |
| **U3 提示与工具更新** | 系统提示、few-shot、工具 schema | 小时级 | 是（配置版本） | 口径调整、新增工具 |
| **U4 权重更新** | 重跑 SFT/DPO（或 CPT） | 天–周级 | 是（adapter 版本） | 语言风格、格式、拒答边界变化 |

**原则**：能用 U1 解决的不上升到 U4。事实类知识 90% 应由 U1 处理——
这正是"知识在检索层、能力在权重层"的架构收益。

### 11.3 更新流程（U1，日常主力）

```text
新文档/勘误
 → ① 入库申请（填 source/license/level，缺项拒收）
 → ② 走 P3 清洗流水线（同一套脚本，不另开路径）
 → ③ 抽检（新增条目 10%，全量双人）
 → ④ 增量索引构建（FAISS 追加 + BM25 重建 + 图谱增量）
 → ⑤ 回归评测（§11.6 的 R1 集，必须零退化）
 → ⑥ 灰度（10% 流量 / 或指定 2 名用户，24 h）
 → ⑦ 全量切换 + 打 tag（corpus-v1.3.2）+ 更新 CHANGELOG
```

**回滚**：`corpus` 与 `index` 均按版本号存目录，切换软链即可；**保留最近 5 个版本**。

### 11.4 决策点 D7-1：这次变更走哪条通道？

按"变的是什么"而不是"有多大工作量"选通道。选错通道是这套系统最常见的退化原因：
把事实塞进 SFT（该走 U1）会让知识不可溯源、不可回滚；把口径写进语料（该走 U3）
会让同一条口径在检索层和提示层各说一遍，冲突时无法判定谁对。

| 变更内容 | 通道 | 判据 |
|---|---|---|
| 新增/修订**事实**（标准条款、材料参数、术语） | **U1** | 能用"检索到的一段原文"回答 → U1 |
| 检索命中率下降、召回不全 | **U2** | 语料没变但 R1 上 A2/H1 退化 → 调切分/重排/融合 |
| 回答**口径/格式/拒答边界**变化 | **U3** | 事实都对但"说法"不对 → 改提示与 few-shot |
| 语言风格、工具调用格式、拒答倾向整体漂移 | **U4** | U3 反复调不动 → 才动权重 |

**硬规则**：同一变更**只允许走一条通道**。若判断需要两条（如"新增标准 + 改口径"），
**拆成两次发布**，先 U1 后 U3，各自跑 R1——否则退化时无法定位是哪一半造成的。

### 11.5 四个评分维度与计算方法

#### 维度 1：准确性（Accuracy）

| 项 | 定义 | 计算 | 门槛 |
|---|---|---|---|
| A1 事实正确率 | 答案与标准答案/原文一致 | 人工判定（3 人盲评，多数票） | ≥ 90% |
| A2 引用正确率 | 引用片段确实支持该结论 | 自动（片段包含关键句）+ 人工抽检 20% | ≥ 95% |
| A3 术语一致性 | 术语用词与本库术语表一致 | 自动（术语表匹配） | ≥ 98% |
| A4 数值一致性 | 答案中的数值与工具返回/原文一致 | **自动**（正则抽取数值 → 与工具 JSON 比对） | **100%** |

A4 是硬性 100%：任何数值不一致都判定为"不合格"，因为它最容易被误信。

#### 维度 2：幻觉控制（Hallucination Control）

| 项 | 定义 | 计算 | 门槛 |
|---|---|---|---|
| H1 无据断言率 | 无引用支撑的事实性断言占比 | 自动（断言切分 + 引用覆盖检查） | ≤ 5% |
| H2 编造引用率 | 引用不存在的文档/页码 | 自动（引用解析 + 库内比对） | **0** |
| H3 过度自信率 | 检索为空/低分时仍给出确定结论 | 自动（检索分数 < 阈值的会话中，语气标记检测） | ≤ 3% |
| H4 正确弃答率 | 应弃答（超纲/受控/越界）时确实弃答 | 人工（专设 60 题"应拒答"集） | ≥ 95% |
| H5 冲突呈现率 | 来源冲突时是否并列呈现 | 人工（专设 30 题冲突集） | ≥ 90% |

**弃答模板**（强制）：`未在本库中找到可支撑的依据。以下为通用知识，未经本地库验证：…（并标注）`。

#### 维度 3：设计推理一致性（Design Reasoning Consistency）

| 项 | 定义 | 计算 | 门槛 |
|---|---|---|---|
| D1 参数-结果一致 | 报告的性能与引擎 JSON 完全一致 | 自动（逐字段比对） | **100%** |
| D2 约束自洽 | 不出现"违反自身给出约束"的方案（如装填分数 >1、喉径为 0） | 自动（规则检查） | **100%** |
| D3 可辨识性提示 | 参数敏感/共线时是否提示（用 `srm sensitivity` 结论） | 自动 + 人工 | ≥ 90% |
| D4 收敛状态如实 | 逆设计残差 >1e-2 时必须标注"未收敛" | 自动 | **100%** |
| D5 方案可比性 | 给多方案时须有同一口径的对比表 | 人工 | ≥ 85% |

**测试方法**：构造 40 个设计任务（8 个族 × 5 组指标），跑完整链路，逐项自动核对。
选族的依据：`GrainFamily` 共 **14 个取值**，其中 **13 个**能用 `default_design_space(family, D, (L0, L1))`
建出设计空间（实测：只有 `custom_polygon` 抛 `ValueError`——它是轮廓数据而非参数化族，
`cylindrical` 是端燃、设计空间只有 `length`）。40 个任务从这 13 个里挑 8 个覆盖
"单孔/多孔/含金属丝/端燃"四类拓扑即可，不必全测。
`verification.checks` 的 6–13 项（§2.3 表）可直接作为 D2 的判定依据——**但只覆盖引擎侧约束**，
"方案违反自身给出的约束"（例如正文说装填分数 0.75、附表写 0.95）仍需规则检查补上。

#### 维度 4：经验可用性（Experience Usability）

| 项 | 定义 | 计算 | 门槛 |
|---|---|---|---|
| E1 可执行性 | 建议是否含可操作步骤/参数/判据 | 人工 5 分制 | ≥ 4.0 |
| E2 边界完整性 | 是否给出适用/不适用条件 | 人工（有/无） | ≥ 95% |
| E3 安全标记 | 安全类回答是否带"须人工复核" | 自动 | **100%** |
| E4 工程师采纳率 | 领域工程师"会照此执行"的比例 | 人工问卷（≥5 人） | ≥ 70% |
| E5 排故有效性 | 排故建议是否命中根因（对照历史案例） | 人工（30 个案例） | ≥ 60% |

E5 门槛设为 60% 而非更高，是因为排故本质是"缩小搜索空间"，能给出正确的前 3 项排查方向即有价值。

### 11.6 评测集构成与回归规则

| 集 | 规模 | 用途 | 更新频率 |
|---|---|---|---|
| R1 回归集（固定） | 300 题（问答 150 / 设计 60 / 工程 60 / 拒答 30） | 每次更新必跑，**零退化** | 季度评审后可增不可改 |
| R2 挑战集 | 100 题（超纲、冲突、多跳、诱导越界） | 季度 | 季度 |

**回归规则**：R1 上任一维度下降 > 2 个百分点 → 阻止上线；
R3 上新增知识命中率 < 80% → 检查索引与切分，不通过则回滚。

### 11.7 评分报告模板（每次发布必出）

```text

┌ 准确性 ──── A1 92.3%  A2 96.1%  A3 99.0%  A4 100%
├ 幻觉 ────── H1 3.8%   H2 0      H3 1.9%   H4 96.7%  H5 93.3%
├ 设计一致性 ─ D1 100%   D2 100%   D3 92.5%  D4 100%   D5 88.3%
├ 经验可用性 ─ E1 4.2/5  E2 96.7%  E3 100%   E4 74%    E5 63.3%
└ 对比上一版: A1 +1.2 / H1 -0.6 / 其余持平       结论: 通过
```

### 11.8 回退方案

- 更新后 R1 退化 → 切回上一版语料/索引软链（分钟级）。
- adapter 更新导致风格漂移 → 只回滚 adapter，保留语料更新（两者解耦是 §9.5 的设计目的）。
- 评测本身失效（题目泄漏进训练集）→ 立即从 R1 剔除该题，重跑并记录；R1 只增不改的原则优先。

## 12. P8：本地访问、长期运行与运维

### 12.1 输入

- 已验收的模型 + adapter（P5）、语料与索引（P3）、Agent 层（P6）、评测基线（P7）。
- 机器清单：GPU 型号/驱动/CUDA、CPU、内存、磁盘（含预留 20%）、UPS。
- 使用方名单与并发预期（决定 §12.5 的单机/双机）。
- 网络现状：**隔离区无外网**，因此所有依赖必须在 P1 已固化，本阶段不允许新增下载。

### 12.2 策略：服务拓扑与依赖顺序（单机）

| 服务 | 端口 | 启动方式 | 说明 |
|---|---|---|---|
| vLLM | 8001 | systemd（容器） | `--max-model-len 32768 --gpu-memory-utilization 0.90 --enable-prefix-caching`；要拿到 §8.2 的 FP8-KV 并发数须再加 `--kv-cache-dtype fp8`（默认 `auto` 即权重精度，此时 KV 是 FP16） |
| llama.cpp（兜底） | 8002 | systemd | 仅在 GPU 故障时手动拉起，模型 Q4 |
| 嵌入服务 | 8003 | systemd | bge-m3，CPU 或 GPU（与 LLM 共享卡时用 CPU） |
| agentd（编排） | 8000 | systemd | 依赖 8001/8003 |
| 前端 | 8080 | nginx（静态） | 复用 `src/srm_open/web/` 风格，无构建链 |
| `srm` 引擎 REST | 8010 | systemd | `srm serve --port 8010`（需 `[api]` extra） |

**依赖顺序**：`vllm → embed → srm-rest → agentd → nginx`，用 systemd `After=`/`Requires=` 固化。

> **端口冲突**：`srm serve` 的默认端口是 **8000**（`api/cli.py` 的 `--port` 默认值），与本表的
> agentd 相同，因此 unit 里**必须显式写 `--port 8010`**；漏写会让两个服务抢同一端口，
> 表现为 agentd 起不来而 `srm` 看起来正常。另外 `serve` 在端口被占用时会**向上顺延最多 20 个
> 端口**（AGENTS.md 记录的启动行为），所以"服务起来了"不等于"起在 8010"——验收脚本要
> `curl http://127.0.0.1:8010/health` 而不是只看进程存活。

### 12.3 长期运行的五个必做项

1. **显存不增长**：`--gpu-memory-utilization 0.90` 留 10% 余量；监控 `nvidia-smi` 显存曲线，
   72 h 内增长 >2% 视为泄漏，需查 KV 块回收与请求超时清理。
2. **请求超时与取消**：客户端断开必须能取消生成（vLLM 默认支持），否则长请求会堆积占满 KV。
3. **日志轮转 + 审计**：问答日志保留 90 天（含输入哈希、检索命中 id、工具调用、输出版本），
   **不记录 D2 原文**（只记 id）；日志目录单独加密。
4. **备份策略**：语料/索引/adapter/配置 每日增量 + 每周全量到离线 HDD；
   模型权重只在变更时备份（体积大）。**恢复演练每季度一次**（这是最容易被跳过、也最容易在事故中致命的一项）。
5. **不可变快照**：每季度打一个 `/opt/agent-<date>` 全量快照（含 wheelhouse + models + corpus + env 锁），
   用于"整机重建"演练。

### 12.4 监控指标（离线 Prometheus 或轻量脚本均可）

| 类别 | 指标 | 告警阈值 |
|---|---|---|
| 服务 | 各端口健康检查失败 | 连续 3 次 |
| 性能 | P95 首 token 延迟 | > 5 s |
| 性能 | 输出速度 | < 15 tok/s |
| 资源 | GPU 显存占用 | > 95% 持续 10 min |
| 资源 | 系统内存 | > 90% |
| 质量 | 日抽样 20 条人工评分 | 均分 < 3.5 |
| 质量 | 弃答率突增 | 环比 +50% |
| 安全 | 越界请求命中 | 任一即告警 |

### 12.5 决策点 D8-1：单机 vs 双机

| 场景 | 建议 |
|---|---|
| ≤8 人、非 7×24 | 单机（T2），接受维护窗口停机 |
| 7×24 或 >8 人 | 双机（推理 + 训练/备用），或 T3 单机多卡 |
| 有"不可停机"要求 | 双机 + 前置负载均衡，模型版本滚动切换 |

### 12.6 回退方案

- GPU 故障 → llama.cpp CPU 通道接管（速度降至 2–9 tok/s，但**服务不中断**，
  UI 显示"降级模式"横幅）。
- vLLM 崩溃 → systemd 自动重启 + 熔断（5 分钟内重启 3 次则停止并告警，避免崩溃循环）。
- 整机故障 → 用最近快照在新机重建（目标 RTO ≤ 4 h，RPO ≤ 24 h）。

## 13. P9：风险清单与验收标准

### 13.1 输入

- 全部阶段的交付物与门禁记录：G0–G8 的签署件、G1 的离线安装日志、G2 的哈希校验输出、
  G3 的数据卡与抽检报告、G4 的基准报告、G5 的训练报告、G6/G7 的评分报告、G8 的压测曲线。
- §11.7 格式的**最近一次**评分报告（这是 V-4/V-5/V-6 的唯一证据来源）。
- 风险登记册的当前状态（本阶段要把它从"计划"变成"已发生/已缓解"的实况）。

### 13.2 策略：先证明"无外连"，再证明"能力达标"

顺序不可换。先做 V-1/V-2/V-3（零外连、可重建、哈希完整）——这三项不过，
后面所有指标都是在"一个说不清来源的系统"上测的，没有意义。通过后再按
V-4→V-12 逐条验收，每条留证据、每条可复现。

**验收不是"再跑一遍测试"**，而是"由**未参与建设**的人按手册复现一遍"。
这是 V-11 存在的理由：自己写的系统自己验收，等于没验收。

### 13.3 风险登记（按"影响 × 概率"排序）

| # | 风险 | 影响 | 概率 | 缓解 | 触发后的动作 |
|---|---|---|---|---|---|
| R-1 | 语料质量不足，答案"像但不对" | 高 | 高 | 无出处不入库；抽检 5%；A2/H1 指标卡口 | 缩小域范围，先做 K1/K4/K9 |
| R-2 | 幻觉被误信为工程结论 | **极高** | 中 | 数值只来自引擎；强制引用；页脚声明；H2 必须为 0 | 立即下线相关回答类型 |
| R-3 | 受控数据误入语料 | **极高** | 中 | 四级分级 + 入库审批 + 静态扫描关键词 | 回滚批次、追查、事件报告 |
| R-4 | 离线依赖不全，装不上 | 中 | 高 | wheelhouse 平台对齐；G1 门禁；整机快照 | 回准备区补齐重摆渡 |
| R-5 | 显存不足/并发 OOM | 中 | 中 | 按 §3.2 反算；留 10% 余量；并发限流 | 降上下文/降量化/加卡 |

### 13.4 风险与"离线"前提的冲突点（必须显式承认）

1. **上游更新拿不到**：隔离环境下无法 `git pull`。缓解：**每次摆渡顺带同步源码镜像**
   （`git bundle create`），冻结在已验证 commit；不做"最新版"追求。
2. **漏洞补丁滞后**：CVE 修复需要人工带外获取。缓解：季度安全评审，按 CVSS ≥7 的清单
   定向摆渡补丁；不在生产网做在线扫描。
3. **模型许可的"在线校验"风险**：某些权重下载时需接受条款（Llama 系列）。
   缓解：在准备区完成审批与下载，**隔离区只使用文件**；`MODEL_CARD.md` 记录审批凭证编号。

### 13.6 决策点 D9-1：验收不通过时怎么处理

验收必然会出现"大部分过、个别不过"。关键是**不许"带条件放行"**——一旦允许，
下一轮就会变成默认。按下面的分流规则处理，每条都写进验收记录。

| 不通过项 | 分流 | 处理 | 是否阻塞上线 |
|---|---|---|---|
| V-1 零外网 / V-3 哈希 / V-10 安全 | **硬阻塞** | 回到对应阶段修，重跑该项 | 是 |
| V-4/V-5/V-6 指标差 ≤2 个百分点 | 有条件 | 缩范围（关闭未达标能力类型），并在 UI 标注"该能力未验收" | 否，但须签署 |
| V-4/V-5/V-6 指标差 >2 个百分点 | 硬阻塞 | 回 P5/P6 重做，不得靠调门槛通过 | 是 |
| V-8 性能不达标 | 有条件 | 降档运行（缩短上下文/换快档模型），记录实测值 | 否 |
| V-9 72 h 不稳定 | 硬阻塞 | 修 vLLM 参数或驱动，重跑满 72 h | 是 |
| V-11 可运维 / V-12 合规 | 硬阻塞 | 补手册 / 补 SBOM | 是 |

**禁止的三种"通过"方式**：改判据、改评测集、把未测项写成"设计满足"。
三者都会让这份验收报告失去意义，且是审计时最先被查出来的地方。

### 13.7 回退方案（验收失败）

- 已上线系统需要换代而新版本验收不过 → **保留旧版本继续服务**，新版本留在旁路，
  这要求 P8 的双版本并存能力（§12.5）。
- 硬件不达标（V-8/V-9）→ 按 §8.6 降档，而不是延期等新硬件。
- 数据合规问题（V-12）→ 立即下线对应语料批次并重跑 R1，见 §11.8。

|---|---|---|

### 14.2 主要取舍表

| 取舍 | 选择 | 放弃 | 理由 |
|---|---|---|---|
| 模型规模 | 32B 级 | 70B | 边际收益低、延迟翻倍、无法单卡训练 |
| 上下文 | 32k | 128k | KV 随上下文线性增长（32B@128k 单序列 32 GiB）；切片可替代 |
| 训练深度 | LoRA/QLoRA | 全参 | 可回滚、多 adapter；全参需 16 B/参数显存（32B 约 525 GiB） |
| 知识注入 | RAG 为主 | 权重灌知识 | 可更新、可溯源、可回滚 |
| 数值来源 | 引擎 | 模型生成 | 唯一能保证 100% 一致的办法 |
| 编排 | 自研薄层 | 重型框架 | 隔离环境可控性优先 |
| 前端 | 复用仓库静态页 | Open WebUI | 无构建链、许可清晰 |
| 图谱 | 可选增强 | 必需组件 | 效果不确定，先做规则版 |

### 14.3 一句话总结

**用 48 GB 级单卡跑 32B-Q4@32k，把事实放进可回滚的检索层，把口径放进可回滚的 adapter，
把所有数值交给 `srm_open` 引擎，用四个维度的自动+人工指标卡住每一次更新。**
这套组合在离线环境下是"可达上限最高、失败模式最可控"的方案；它不追求单点最强模型，
而是让每个环节的错误都能被检出、被回退。

### B.2 事实复核（准备区一次性执行）

§0.2 的星标/许可证/推送时间可在**准备区**（唯一可联网环节）原样重跑；隔离区内不要执行。

```bash
# GitHub：仓库事实（full_name / stars / license / pushed_at）
for r in ggml-org/llama.cpp vllm-project/vllm sgl-project/sglang Niko1221/Strata \
         simplexai-labs/PolyStrata hiyouga/LlamaFactory huggingface/peft \
         unslothai/unsloth infiniflow/ragflow HKUDS/LightRAG microsoft/graphrag \
         docling-project/docling microsoft/markitdown facebookresearch/faiss \
         lancedb/lancedb open-webui/open-webui; do
  curl -s "https://api.github.com/repos/$r" | python3 -c \
    "import json,sys;d=json.load(sys.stdin);print(d['full_name'],d['stargazers_count'],
     (d.get('license') or {}).get('spdx_id'),d['pushed_at'][:10])"
done

# LocModel：同名社区仓库不止一个，必须列出再判断
curl -s "https://api.github.com/search/repositories?q=LocModel&sort=stars&per_page=8" | python3 -c \
  "import json,sys;[print(i['full_name'],i['stargazers_count'],(i.get('license') or {}).get('spdx_id'))
   for i in json.load(sys.stdin)['items']]"

# HuggingFace：权重许可证（cardData.license）
for m in Qwen/Qwen3-8B Qwen/Qwen3-30B-A3B Qwen/Qwen2.5-32B-Instruct \

done
```
